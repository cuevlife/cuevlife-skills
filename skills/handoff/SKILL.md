# handoff

ไฟล์เดียว `HANDOFF.md` ที่รากโปรเจกต์ อัปเดตทับทุกครั้ง ไม่สร้างไฟล์ใหม่ อ่านจบใน 1-2 นาที
ผู้อ่านคือ session ใหม่หรือคนอื่นที่ไม่รู้บริบทเลย

## คำสั่ง

- **"เขียน handoff"** → ทำตามหัวข้อ "เขียน" ด้านล่าง
- **"read handoff"** → ทำตามหัวข้อ "อ่าน" ด้านล่าง
- **"handoff init"** → สร้าง `HANDOFF.md` ในโปรเจกต์ปัจจุบัน (ทำตามหัวข้อ "init") ใช้ตอนเข้าโปรเจกต์ใหม่หรือโปรเจกต์ที่ยังไม่มีไฟล์
- ถ้าสั่ง "เขียน handoff" แต่ยังไม่มี `HANDOFF.md` → ทำ init ต่อเลย ไม่ต้องถามกลับ
- ผู้ใช้บอกว่าจบงาน/พักแล้ว แต่ไม่ได้สั่ง → เสนอ 1 บรรทัดว่าจะ "เขียน handoff" ไหม อย่าเขียนเองโดยไม่ได้สั่ง

## เขียน

1. **เก็บข้อเท็จจริงจากของจริงก่อน ไม่ใช่จากความจำ**: รัน `git status`, `git log -5 --oneline`, `git diff --stat` และเปิด `HANDOFF.md` เดิม (ถ้ามี)
2. อัปเดตไฟล์ทับ ของใหม่อยู่บนสุด โครงตามด้านล่าง เขียนไทย กระชับ คงชื่อไฟล์/ตัวแปร/คำสั่งเป็นอังกฤษตามเดิม
3. ย้ายเนื้อหารอบก่อนที่ยังจริงอยู่ขึ้นมารวมในหัวข้อปัจจุบัน ส่วนที่จบแล้วให้ย่อเหลือ 1-2 บรรทัดใน "ประวัติรอบก่อน" เก็บไว้ไม่เกิน 10 รอบ ตัดของเก่าสุดทิ้ง
4. **ตรวจความลับก่อนบันทึก** (ดู "ห้ามเขียน") แล้วบอกผู้ใช้สั้นๆ ว่าเขียนไปที่ไหน และมีอะไรที่ระบุว่า "ยังไม่ยืนยัน" บ้าง

### โครงไฟล์

```markdown
# Handoff — <ชื่อโปรเจกต์>
อัปเดตล่าสุด: <วัน เดือนเต็ม พ.ศ.> (<YYYY-MM-DD>)

## 1. สถานะปัจจุบัน
- เสร็จ: ...
- ค้าง: ... (ทำถึงไหน เหลืออะไร)
- รอ: ... (รอใคร/รออะไร)
- ยังไม่ยืนยัน: ... (สิ่งที่คิดว่าจริงแต่ยังไม่ได้ทดสอบ/ตรวจ)
- Branch / uncommitted: <branch> · <สรุปไฟล์ที่ยังไม่ commit ตาม git status>

## 2. ทำรอบนี้
- <สิ่งที่ทำ 3-8 ข้อ>

## 3. ของอยู่ที่ไหน
- <path> — <มีอะไร/ทำไมสำคัญ>
- คำสั่งรัน/เทสต์: `...`

## 4. การตัดสินใจ
- **เลือก:** X · **เหตุผล:** ... · **ปัดตก:** Y เพราะ ...
  (ทุกข้อต้องมีครบทั้งเหตุผลและทางเลือกที่ปัดตก ถ้าไม่มีทางเลือกอื่นให้เขียนว่า "ไม่มีทางเลือกอื่นที่พิจารณา")

## 5. กับดัก / ข้อห้าม
- บั๊กที่เจอแล้ว: อาการ → สาเหตุ → วิธีแก้ (หรือ "ยังไม่รู้สาเหตุ")
- ห้ามทำ: ... เพราะ ...

## 6. งานถัดไป
1. <ข้อแรกที่ควรทำ ระบุไฟล์/คำสั่งชัดพอเริ่มได้เลย>
2. ...

## 7. ประวัติรอบก่อน (ใหม่สุดอยู่บน)
- <วันที่เต็ม> — <1-2 บรรทัด>
```

### กติกาเนื้อหา

- วันที่เขียนเต็มเสมอ (เช่น 21 กันยายน 2569 หรือ 2026-09-21) ห้ามใช้ เมื่อวาน/พรุ่งนี้/สัปดาห์หน้า
- ห้ามเดาหรือแต่งข้อมูล สิ่งที่ไม่ได้รัน/ไม่ได้เปิดดูจริง ให้ลงใน "ยังไม่ยืนยัน" ไม่ใช่ใน "เสร็จ"
- "เสร็จ" ต้องมีหลักฐาน (เทสต์ผ่าน, เปิดหน้าดูแล้ว, commit hash) ไม่งั้นเขียนว่า "ทำแล้วแต่ยังไม่ทดสอบ"
- งานค้างครึ่งทางต้องบอกจุดที่หยุดชัดๆ (ไฟล์/ฟังก์ชัน/บรรทัดที่ทำถึง) และสิ่งที่ยังไม่ได้ทำในไฟล์นั้น
- กับดักและบั๊กที่เจอแล้วต้องจดทุกครั้ง แม้แก้ไปแล้ว ถ้ามีโอกาสเจอซ้ำ
- ข้อความเขียนให้คนที่ไม่รู้จักโปรเจกต์อ่านรู้เรื่อง: อย่าใช้คำย่อ/ชื่อเล่นที่ไม่อธิบาย

### ห้ามเขียน (ห้ามเด็ดขาด)

- รหัสผ่าน, key, token, ค่าใน `.env` (เช่น `AUDIT_KEY`, `OWNER_TOKEN`, DB/FTP credentials) — บอกได้แค่ชื่อตัวแปรและว่าอยู่ที่ไหน
- ข้อมูลลูกค้า/ลูกหนี้จริง (ชื่อ เบอร์ ที่อยู่ ยอดหนี้ของคนจริง) — อ้างด้วยเลขสัญญา/id หรือข้อมูลสมมติ
- หมายเลข IP / host / path ของ production — เขียนว่า "FTP production" เฉยๆ
- ข้อมูลส่วนตัวของคนอื่น (ชื่อทีม อีเมล) — อ้างเป็นบทบาท

ถ้าเจอของพวกนี้ในไฟล์เดิมหรือในผลลัพธ์คำสั่งที่จะลอกมา ให้ตัดออกหรือแทนด้วยคำอธิบายก่อนบันทึก

## init

1. ที่รากโปรเจกต์ (โฟลเดอร์ที่มี `.git` หรือ cwd ถ้าไม่มี git) ถ้ามี `HANDOFF.md` แล้ว → ไม่เขียนทับ ไปทำ "เขียน" แทน
2. สำรวจเอกสารที่มีอยู่: `*.md` ที่ราก (README, ROADMAP, TODO, CHANGELOG, NOTES, docs/) + `CLAUDE.md`/`AGENTS.md` + `git log -10`, `git status`
3. **ดึงเฉพาะสิ่งที่ handoff ต้องใช้** ลงหัวข้อที่ตรงกัน แล้วย่อให้สั้น ห้ามคัดลอกทั้งก้อน:
   - งานค้าง/รอ/แผนถัดไป → หัวข้อ 1 และ 6
   - ของที่ตัดออก/ทางที่ปัดตกแล้ว + เหตุผล → หัวข้อ 4
   - บั๊กที่เจอ/ข้อห้าม/ข้อจำกัดของ environment → หัวข้อ 5
   - สิ่งที่อธิบายโครงสร้างระบบถาวร (สถาปัตยกรรม, schema, route) ไม่ต้องลอก ให้ชี้ไปที่ไฟล์นั้น (เช่น "โครงระบบดู `CLAUDE.md`") กันข้อมูลซ้ำสองที่แล้วขัดกันในภายหลัง
4. สิ่งที่อ่านมาแต่ยืนยันไม่ได้ (เอกสารเก่า, ลงวันที่ก่อนหน้า) ให้ลงเป็น "ยังไม่ยืนยัน" พร้อมบอกวันที่ของเอกสารต้นทาง
5. **ห้ามลบ/แก้/ย้ายเอกสารต้นทาง** เอง แม้ข้อมูลถูกรวมเข้า handoff แล้ว ให้บอกผู้ใช้ว่าไฟล์ไหนซ้ำกับ handoff แล้วให้ตัดสินใจเอง
6. หลังสร้าง เช็ก `.gitignore` ว่าไฟล์จะถูก track ไหม แล้วบอกผู้ใช้ 1 บรรทัด (ไม่แก้ `.gitignore` เอง)

## อ่าน

1. อ่าน `HANDOFF.md` ทั้งไฟล์ ถ้าไม่มี → บอกว่ายังไม่มี handoff แล้วถามว่าจะเริ่มจากอะไร (อย่าเดาสถานะจากความจำ)
2. **ตรวจว่าไฟล์ยังตรงความจริง**: เทียบวันที่อัปเดตกับ `git log` และเทียบรายการ uncommitted กับ `git status` ถ้าไม่ตรง (มี commit ใหม่กว่า/ไฟล์เปลี่ยนหลังจากนั้น) ให้บอกความต่างก่อนทำต่อ
3. สรุปให้ผู้ใช้ไม่เกิน 5 บรรทัด: สถานะ, งานค้าง, งานถัดไปข้อแรก, กับดักที่ต้องระวัง, สิ่งที่ยังไม่ยืนยัน
4. ทำ "งานถัดไป" ข้อแรกต่อได้เลยถ้าชัดเจน ไม่ต้องถามซ้ำ ถามเฉพาะเมื่อ handoff ระบุว่ารอการตัดสินใจจากผู้ใช้ หรือมี "ยังไม่ยืนยัน" ที่กระทบงานข้อแรก
